# 第三课：控制变量、重复实验与断点续训

前一阶段比较了五种不同模型。这能描述它们在固定配方下的表现，但不能单独回答“是不是层数更多，所以准确率更高”：架构、参数量、计算方式都同时变了。本阶段在同一 CNN 家族里改变少数因素，改善这个问题。

## 我们实际执行的方案

共同设置为 Fashion-MNIST、固定原划分、20 epochs、Adam、lr=0.001、AMP、无数据增强与权重衰减。每种配置使用 42、43、44 三个种子。选模仍用最低验证损失。

模型有三个阶段，输出通道数为 W、2W、4W；每阶段重复 d 次卷积、BN 和 ReLU，末尾池化。共 3d 个卷积层。最后全局平均池化并输出十类分数。

| 问题 | 改变 | 固定 | 仍需承认的限制 |
|---|---|---|---|
| 更深有何影响？ | 3、6、9 个卷积层 | W=32，batch=128 | 参数量也会增加 |
| 容量更大有何影响？ | W=16、32、64 | 6 个卷积层，batch=128 | 通道数和计算量也一起变化 |
| batch 有何影响？ | 32、64、128、256 | 6 个卷积层，W=32 | 更新次数和 BN 批统计也会变化 |
| 参数量相近时深度有何影响？ | (d,W)=(1,48)/(2,27)/(3,21) | 约 20.5—21.0 万参数 | 宽度无法同时保持相同 |

一些配置同时属于多个比较组，所以去重后为 11 种，不是把所有组的行数直接相加。每种三个种子，共 33 次训练。实验定义已经固化在 reports/ablation_plan.json，不能看过测试结果再修改这个清单。

## 为什么重复三个种子

不同种子会改变初始参数和训练顺序。一次表现最好可能只是随机波动。因此我们保留每次结果，并报告三个种子的平均值和样本标准差：

`平均值 = (a₁+a₂+a₃)/3`

`样本标准差 = sqrt(((a₁-平均值)²+(a₂-平均值)²+(a₃-平均值)²)/2)`

这里分母为 n−1=2。标准差反映这三次训练的波动，不是置信区间，也不包含重新划分数据带来的不确定性。不要只挑三个种子中最高的一个作为该配置的结论。

## 固定轮数并不等于固定更新次数

54000 张训练图、20 轮时：

| batch size | 每轮 batch 数 | 计划更新次数 |
|---:|---:|---:|
| 32 | 1688 | 33760 |
| 64 | 844 | 16880 |
| 128 | 422 | 8440 |
| 256 | 211 | 4220 |

因此，小 batch 既改变了每次梯度估计的样本量，也增加了更新次数。本实验回答的是“固定数据遍历预算下的效果与成本”。另外，GradScaler 可能跳过非有限梯度导致的更新，因此程序使用优化器步骤钩子记录实际更新次数，不能简单假定它总等于计划次数。

## best.pt 与 last.pt 分别有什么用

`best.pt` 保存按验证损失选出的模型，主要用于最终评估。

`last.pt` 保存最后完整轮次的训练状态，包括模型参数与 BN 缓冲区、Adam 状态、GradScaler、Python/NumPy/PyTorch/CUDA 随机状态、DataLoader 随机生成器、日志历史、最佳模型副本等。续训需要这些信息，因为仅有模型权重无法重建优化器和后续随机顺序。

每轮先写临时文件，再原子替换 last.pt。若训练在轮次中途退出，恢复时重新跑这一轮，最多损失当前未保存轮次的计算。日志和汇总以检查点内保存的完整历史为准，不把未完成的半轮当成有效结果。

已完成两类验证：CPU 上含 Adam、Dropout 和打乱顺序的训练，恢复后与不中断的下一轮参数逐位一致；实际 GPU 配置在第 1 轮保存退出后，成功恢复并完成第 2 轮。另检查了 AMP 更新计数、验证不改变模型状态与队列锁。这里不承诺跨硬件、驱动或库版本的 GPU 逐位一致。

## 如何查看或继续

项目根目录的“进度与续跑.md”每轮刷新，显示全部 33 次训练的已保存轮数、完成情况和续跑命令。机器可读状态在 reports/ablations/progress.json，后台日志在 queue.log，错误日志在 queue.err。

恢复命令为：

```powershell
Set-Location 'D:\深度学习作业'
& 'D:\Anaconda\envs\ai-lab\python.exe' -u run_ablations.py
```

程序自动跳过完成项、恢复未完成项，并核对代码、数据划分、配置与运行环境。若已有队列运行，锁会阻止重复启动。休眠或关机不会让 Python 继续计算，重新开机后使用上述命令恢复。

如确实需要主动暂停，可以创建 reports/ablations/STOP_AFTER_EPOCH 文件；队列会在完整轮次存盘后退出。继续前移走这个文件，再运行恢复命令。

当前已找到 Codex 账户额度读取工具，可在聊天中按需检查 5 小时和周窗口的使用情况；最近一次快照保存在 reports/ablations/usage_snapshot.json。这是整个账户的用量，不等于本实验单独消耗的用量。训练脚本本身不查询账户额度，始终每轮存盘，避免依赖临近额度耗尽时才保存。训练是本机 Python 进程；即使聊天无法继续，也已有检查点、源代码和续跑说明。

## 完成后怎么看结果

队列先训练全部 33 次，再统一测试和生成 reports/ablations/summary.md。预测本身也先原子存盘，若制图途中退出，可以复用已保存的预测。汇总重新计算 Accuracy、Macro-F1、混淆矩阵，核对选中轮次、数据划分、实际更新次数和检查点哈希。

分析顺序：先看单次记录和三个种子的波动，再看准确率与参数量、耗时、显存之间的关系，最后结合训练曲线解释。不要只凭图中均值的排序就宣布某种深度或 batch 普遍最优。
